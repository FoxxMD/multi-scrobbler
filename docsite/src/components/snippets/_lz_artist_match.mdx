The Listenbrainz `listens` payload has many fields of varying granularity: (See [OpenAPI Spec](https://rain0r.github.io/listenbrainz-openapi) `listensForUser_payload_listens_inner` schema).

Relevant to MS, an LZ listen can contain one or more, different, **artist fields** that contain varying amounts of rich data, not all of which are guaranteed to be reliable.

<details>

<summary>Artist Fields and Assumptions</summary>

* Reported by the LZ *Client*
  * `track_metadata.artist_name` - a single string with all artists like `Foo and Bar feat. Cool Guy`
  * `track_metadata.additional_info.artist_names` - a list of artist names like `['Foo','Bar','Cool Guy']`
  * `track_metadata.additional_info.artist_mbids` - a list of artist [MBIDs](https://musicbrainz.org/doc/MusicBrainz_Identifier)
* Reported by the LZ Client **or** LZ Server
  * `track_metadata.mbid_mapping.artist_mbids` - a list of artist MBIDs
  * `track_metadata.mbid_mapping.artists` - a list of artist objects like `{artist_credit_name: 'Cool Guy', join_phrase: 'feat.', artist_mbid: '...'}`

All of these fields, other than `track_metadata.artist_name`, are **optional.** Also, critically, these two assumptions apply:

* `mbid_mapping.*` is *usually* only reported by a Listenbrainz Server but can *also* be provided by a LZ Client.
* When LZ reports `mbid_mapping.*` this is because it "matched" your payload data `artist_name` etc... with a Musicbrainz recording.
  * LZ **does not** provide a confidence metric to tell you how likely this mapping is actually correct

</details>

___

For MS to be as accurate as possible for things like [deduplicating scrobbles](/configuration/duplicates/) and providing [good data to scrobble enhancements](/configuration/transforms/) it needs **artist** data to be as granular as possible since different Clients and Sources can report artists in various forms.

Because the LZ payload data can be so ambiguous MS processes LZ payload data through a more rigorous form of the [Native Stage](/configuration/transforms/native/) to try to extract, and match, artist data from all the fields mentioned above. In this case, more rigor => MS only modifies artist data when it has very high confidence it matches the original data well, backed by [25+ tests](https://github.com/FoxxMD/multi-scrobbler/blob/master/src/backend/tests/listenbrainz/listenbrainz.test.ts).

It also enables "smarter" decisions about LZ **Source** data that includes `mbid_mapping` because it's possible the matched mappings *do not* actually align with the data you submitted: MS does string comparisons against these and if they are not highly aligned it falls back to the less-rich `additional_info` and `artist_name` fields instead of using the *mismatched* `mbid_mappings`.

This additional processing is **enabled by default** because most users benefit from this strict matching and corrections.
___

However, there are usecases where you may not want this additional processing to occur such as:

* You know your Listenbrainz Endpoint/Source has high quality matches/submission data that must stay byte-equivalent or contains many already-corrected for edge cases you don't want MS to modify
* You are using MS to forward Now Playing data with `artist_name` fields formatted exactly as you already want them, which MS should not change
* You are transferring scrobbles between LZ servers and want byte-equivalant scrobbles for data preservation/archiving

If your usecase meets this scenario, or you just generally don't want MS doing anything with artists, you can **disable artist extraction** using one of these options in your config:

* File/AIO - use `"options": {"extractArtists": false }`
* ENV - use <CodeInline>{props.name}_EXTRACT_ARTISTS=false</CodeInline>
