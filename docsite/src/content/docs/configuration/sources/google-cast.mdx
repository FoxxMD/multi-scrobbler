If your media device can be **Cast** to using this button ![Chromecast Icon](https://upload.wikimedia.org/wikipedia/commons/2/26/Chromecast_cast_button_icon.svg) on your phone/computer then multi-scrobbler can monitor it in order to scrobble music you play.

:::note 

This source relies on common, **basic** music data provided by the cast device which will always be less exhaustive than data parsed from full source integrations. If there is an existing [Source](/configuration/sources) it is recommended to configure for it and blacklist the app on Google Cast, rather than relying solely on Google Cast for scrobbling.

:::

#### Connecting Devices

Cast devices can be manually configured using file-based configuration OR automatically discovered using **mDNS.**

##### Manual Configuration

Add each device's name and IP address to `devices` in the file-based config. This works with every installation method, including Docker with default (bridge) networking. When `devices` is set, mDNS discovery is disabled unless `useAutoDiscovery` is explicitly set to `true`.

```json5 title="chromecast.json"
[
  {
    "name": "MyCast",
    "type": "chromecast",
    "data": {
      "devices": [
        {"name": "Living Room TV", "address": "192.168.0.115"}
      ]
    }
  }
]
```

##### mDNS Discovery

MS can also discover cast devices by listening for mDNS traffic on port 5353/UDP. The machine running MS must be able to send and receive multicast traffic on the same network as your cast devices.

* **Local installation:** no additional setup is required, other than allowing 5353/UDP through the host's firewall.
* **Docker with [host networking](https://docs.docker.com/engine/network/drivers/host/)** (`network_mode: host`): no additional setup is required.
* **Docker with default (bridge) networking:** containers can't see multicast traffic from the host's network. Configure devices [manually](#manual-configuration) or add an mDNS reflector to your stack as described below.

<Aside type="caution" title="Avahi support was removed">

Previous versions of MS used the host's Avahi daemon for discovery in Docker. This is no longer supported. If you mounted `/var/run/dbus` and `/var/run/avahi-daemon/socket` into the container or set `useAvahi` in your config, remove them.

</Aside>

<DetailsAdmo type="note" summary="mDNS Reflector with Docker">

[`dockurr/mdns`](https://github.com/dockur/mdns) runs on the host's network and copies mDNS traffic between your LAN and the Docker network MS uses, so MS can discover devices while staying on a bridge network.

Add it to the same compose stack as MS and give MS's network a fixed bridge name:

```yaml title="docker-compose.yml" placeholder="LAN_INTERFACE,br-ms"
services:
  multi-scrobbler:
    image: foxxmd/multi-scrobbler
    # ...your existing environment, volumes, ports, etc.
    networks: # [!code highlight]
      - ms # [!code highlight]

  mdns: # [!code highlight]
    image: dockurr/mdns # [!code highlight]
    network_mode: host # [!code highlight] [!ref] The host's firewall must allow 5353/UDP on both interfaces.
    environment: # [!code highlight]
      INTERFACES: "LAN_INTERFACE br-ms" # [!code highlight] [!ref] Replace `LAN_INTERFACE` with the name of the host's network interface on your LAN, such as `eth0`, `enp3s0` or `wlan0`. [!ref] The second interface name must match `com.docker.network.bridge.name`. If MS already uses a network you created, add the same `driver_opts` to it and recreate the network.
    restart: on-failure:3 # [!code highlight] [!ref] The reflector exits if the LAN interface is not connected, for example while Wi-Fi is still connecting at boot. `restart: on-failure:3` retries a few times instead of restarting forever.

networks: # [!code highlight]
  ms: # [!code highlight]
    driver_opts: # [!code highlight]
      com.docker.network.bridge.name: br-ms # [!code highlight] [!ref] Be aware that **all** mDNS traffic is copied between your LAN and the `ms` network, not only Google Cast traffic.
```

</DetailsAdmo>

#### What Media Does MS Scrobble?

Cast devices report what type of media the current activity is [(see `metadata` property here)](https://developers.google.com/cast/docs/media/messages#MediaInformation). The reported type is dependent on the application playing the media to correctly report it, the cast device does not magically know what the media is. If an application does not report a type it is always classified as `unknown`.

**By default, MS will only track media that is reported as `MusicTrack`.**

##### Allow Unknown Media Type

Media with an Unknown (`Generic`) media type can be explicitly allowed by setting `"allowUnknownMedia": true` in the file-based configuration. This can also be configured to only allow unknown media types for specific applications by using a list of application names.

<details>

    <summary>Example</summary>

    ```json5 title="chromecast.json" brackets
    [
      {
        "name": "MyCast",
        "type": "chromecast",
        "data": {
          // [!code highlight] [!ref] only allow unknown if app name contains any of these phrases
          "allowUnknownMedia": ["smarttube", "default media receiver"]
        },
      }
    ]
    ```

</details>

##### Forcing Media Tracking

MS can be forced to track media from an application regardless of media type. This is useful if an application incorrectly reports a media type you are sure should be music. Set `"forceMediaRecognitionOn"` in the file-based configuration to a list of application names that should always be tracked.

<details>

    <summary>Example</summary>

    ```json5 title="chromecast.json" brackets
    [
      {
        "name": "MyCast",
        "type": "chromecast",
        "data": {
          // [!code highlight] [!ref] media from applications that contains these phrases will always be tracked, regardless of media type reported
          "forceMediaRecognitionOn": ["smarttube", "default media receiver"]
        },
      }
    ]
    ```

</details>

#### Cast Troubleshooting

Please include any/all logs with raw output if there are any errors encountered as this is critical to diagnosing issues.

To diagnose bad/incomplete track information or strange MS player behavior please turn on **payload logging** and include log output of the source running to help diagnose this issue. Either enable in config using the below example OR enable [Debug Mode.](/configuration#debug-mode)

<details>

    <summary>Example</summary>

    ```json5 title="chromecast.json" brackets
    [
      {
        "name": "MyCast",
        "type": "chromecast",
        "data": {
          //...
        },
        "options": {
          "logPayload": true // [!code highlight]
        }
      }
    ]
    ```

</details>
